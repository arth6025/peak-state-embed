Peak State Embed

The full Peak State registration flow, plugged into an organiser's own website, so clubs keep their SEO traffic and brand while Peak State keeps checkout and the GMV take.

4 embed modes13 defined screensBackend-enabled per organiserV1 pilot · 3 clubs

TL;DR

Peak State Embed puts the full Peak State registration flow (event, tickets, form, OTP, payment, ticket) inside an organiser's own website, while event pages stay crawlable on the organiser's domain. Peak State still owns checkout, payments and the attendee record, so the GMV take is unchanged.

Why now. Clubs like Find Your Fit, Break Free Club and Sisters in Sweat want two things we can't give them today: SEO traffic landing on their site, and bookings that feel like their brand. If we don't, they move to a tool that does, and we lose the GMV.

What we ship, in one line: a script tag that drops an SEO-friendly event listing onto any site, plus a Peak State checkout that opens over it without leaving the page. Everything is switched on per organiser from the backend.

Assumption to confirm: the attendee flow below is modelled on a standard Peak State checkout (ticket select → details → phone OTP → UPI/card payment → QR ticket). Swap in the real screens where they differ.

Teardown: what KonfHub ships, and why it isn't enough

KonfHub's embed is a plain iframe of their ticket page, configured in a 6-step wizard (KonfHub blog). It keeps registration on the host page, but it gives the organiser almost none of what our clubs are asking for.

What KonfHub doesWhere it falls short for run clubsWhat Peak State does instead
Two widget types: Standard (ticket select first) and Quick Registration (form first)One event per widget; no "all our upcoming runs" view, which is how clubs actually sellListing, single-event and button modes from one script; a club's whole calendar stays in sync
Output is an iframe snippetIframe content is indexed as KonfHub's, not the organiser's: zero SEO value to the host siteEvent content renders into the host page's DOM with schema.org Event markup; only checkout is framed
Theme colours, preselected tickets, show/hide descriptionFixed iframe height and generic look; no brand fonts, no dark modeDesign tokens (colour, font, radius, mode) plus auto-resizing frame
Setup: Developers → Widgets → CreateBuried under "Developers"; most club owners run Wix, Framer or Instagram link pages, not devsEmbeds live in the main nav, with platform guides and a "send to my developer" email
No events back to the host page (not described)Organiser can't fire their Meta pixel or GA4 on purchase; no attributionpostMessage events + a dataLayer push on every step; UTMs carried into the order
No payment detail (not described)UPI intent and 3-D Secure often break inside iframes on mobilePayment step hands off to a top-level Peak State tab on mobile, then returns

The bar to beat is simple: KonfHub moves a form onto your site. We move the traffic, the brand and the data onto it too.

Proposal: four embed modes, one checkout

Every mode ends in the same Peak State checkout, so there is one payment flow to maintain and one attendee record. Modes differ only in what shows on the host page before checkout opens.

ModeWhat appears on the organiser's siteSEO value to organiserBest forPhase
1. Event listingAll upcoming events as cards (date, location, price, spots left), filterable by city or seriesHigh: rendered in host DOM + JSON-LD per eventClub homepage, /events pageV1
2. Event page blockOne event: hero, description, route, ticket tiers, FAQs, inline "Book"High: one indexable page per eventDedicated race or run pageV1
3. Book buttonA branded button anywhere (blog post, Linktree-style page)None by itself; pairs with 1 or 2Instagram bio pages, partner sitesV1
4. Hosted pages on organiser domainPeak State serves full event pages at e.g. events.findyourfit.in via CNAMEHighest: server-rendered, organiser's domain, sitemap includedClubs with no developer or a weak siteV2

Checkout behaviour (all modes). Clicking Book opens a Peak State checkout as a slide-over on desktop and a full-screen sheet on mobile. It runs ticket select, attendee details, OTP, payment and confirmation without leaving the organiser's page. A returning Peak State user is recognised and their details prefilled.

What stays Peak State. Payments, refunds, attendee data, check-in QR and the GMV fee. The organiser gets a copy of each order via webhook and the dashboard, but the transaction is ours.

Out of scope for V1: a headless API for clubs to build their own checkout, white-labelling the Peak State name off the payment step, and multi-organiser marketplaces on a third-party site.

Technical architecture

The core decision: render event content into the host page (for SEO and brand), and frame only the checkout (for payments, security and one code path).

Install. One snippet works on any site builder:

<div id="peakstate-events"></div>
<script src="https://embed.peakstate.in/v1/loader.js" data-embed="emb_fyf_7k2" async></script>

How each part works

  • Loader (~15 KB): reads data-embed, calls the Embed API, renders cards inside a Shadow DOM web component so club CSS can't break ours, and injects one JSON-LD Event block per event (name, date, location, offers, organiser = the club).
  • SEO: Google renders JS, but for reliability we also offer a server snippet: GET /v1/embeds/{id}/html returns static HTML + JSON-LD the club can paste or a WordPress plugin can cache. Each event links to a club URL such as findyourfit.in/events/sunday-10k, never to peakstate.in.
  • Checkout: an iframe on checkout.peakstate.in, opened as a slide-over. It sends ps:ready, ps:resize, ps:ticket_selected, ps:checkout_started, ps:payment_success, ps:closed via postMessage; the loader re-emits them as window.dataLayer pushes so the club's GA4 and Meta pixel fire on their own domain.
  • Session: third-party cookies are blocked in Safari and increasingly Chrome, so the iframe uses phone OTP each time, with partitioned storage (CHIPS) to remember the user on the same club site. Prefill on first visit uses the Storage Access API where available.
  • Mobile payments: UPI intent and 3-D Secure redirects are unreliable inside iframes. On mobile, the payment step opens a top-level Peak State tab and returns to the host page via return_url, restoring the checkout state.
  • Security: CSP frame-ancestors and CORS limited to the organiser's verified domains; embed IDs are public, so nothing sensitive rides on them; webhook bodies are HMAC-signed.
  • Attribution: the loader captures UTMs and document.referrer on the host page and passes them into the checkout, so they land on the order's utm column.

Success metrics, phasing and open questions

Metrics (targets to set after the pilot baseline)

  • Share of pilot clubs' GMV booked through embeds
  • Embed checkout conversion: Book clicked → order paid, desktop vs mobile
  • Mobile payment completion on the UPI hand-off vs in-app checkout
  • Organic sessions to clubs' event pages (from their GA4)
  • Time from A1 switch-on to first live embed

Phasing

  1. V1 pilot (Find Your Fit, Break Free Club, Sisters in Sweat): A1, O1–O6, listing + event block + button, slide-over checkout, webhooks, GA4/Meta events.
  2. V1.1: install checker, platform guides, "email my developer", embed analytics on O1.
  3. V2: hosted pages on organiser domain (CNAME + auto SSL + sitemap), WordPress plugin, series/membership passes.

Open questions

  • Do we charge the same GMV % on embed orders, or a lower one to win clubs who would otherwise self-host?
  • Who owns the attendee for marketing: can the organiser export phone and email, and can Peak State still market to them?
  • Is "Secured by Peak State" on the checkout a must, or can top clubs remove it?
  • Which payment gateway rules apply to UPI intent from an embedded context; does our gateway allow the frame at all?
  • Confirm the real Peak State checkout screens so E2–E6 match production.
